# Defenses Against Prompt Injection in Large Language Model Applications

## Introduction

Large language model (LLM) applications increasingly pair natural-language interfaces with external tooling, persistent storage, retrieval pipelines, and autonomous planning routines. While these integrations allow models to execute complex tasks beyond static text generation, they also tie application security directly to the model's interpretation of untrusted input. Prompt injection and jailbreak attacks exploit this relationship by steering the system toward attacker-supplied instructions. As Tanveer (2026) notes, this vulnerability is structural: because natural-language instructions and data share a single neural processing pathway, their operational boundaries remain permeable.

The severity of this issue is reflected in industry benchmarks. Prompt injection has held the top position in the OWASP Top 10 for Large Language Model Applications since 2023, and agentic goal hijacking was ranked first in the December 2025 OWASP Top 10 for Agentic Applications (Tanveer, 2026). In agentic environments, an injected instruction can compromise multi-step workflows across planning stages, memory lookups, tool invocations, and final outputs. Documented vulnerabilities, such as exploits affecting GitHub Copilot and CamoLeak (Tanveer, 2026), demonstrate that indirect prompt injection presents immediate operational hazards rather than abstract theoretical risks.

Securing these systems requires more than isolated system prompts or standalone classifiers. This paper examines four complementary defensive layers: input validation and filtering, instruction hierarchy enforcement, output controls, and runtime monitoring. While each mechanism addresses a specific vector, none offers complete protection against adaptive adversaries. Building resilient applications demands a defense-in-depth posture that bounds untrusted inputs, establishes strict directive authority, validates all downstream actions, and monitors execution state continuously.

## Prompt injection attack taxonomy

Prompt injection redirects an LLM application toward attacker-dictated actions. Liu et al. (2024) define the primary outcome as model execution dictated by injected payload content instead of authentic user instructions. Direct attacks deliver hostile inputs directly through the user interface, whereas indirect attacks embed payloads within external data sources ingested during execution. Tanveer (2026) emphasizes that retrieval-augmented pipelines and autonomous agents are especially susceptible to indirect vectors, as they routinely pull external text into the active model context.

Direct injections typically aim to subvert developer constraints, leak private context, or execute unauthorized operations. Closely related jailbreak techniques use adversarial prompting to bypass alignment guardrails. Surveying various methodologies, Mathew (2024) reports widespread success in misleading major model families. Defenses anchored to simple heuristic string matching (such as "ignore previous instructions") fail to generalize against semantic obfuscation, roleplay scenarios, multilingual inputs, or algorithmically optimized payloads.

Automated generation techniques further highlight the fragility of signature-based defenses. Liu et al. (2024) introduce a gradient-based framework for synthesizing universal prompt injections, demonstrating that these vectors routinely bypass conventional filters. Their findings indicate that gradient-driven evaluations are essential to prevent overestimating system robustness; successfully repelling a static test suite does not imply that the underlying attack surface has been closed.

In agentic architectures, the threat shifts from generating harmful text to complete goal hijacking. When processing web pages, database entries, user documents, or API responses, a model may mistakenly prioritize embedded text over its core task. Tanveer (2026) observes that adding tool access, persistent memory, and Model Context Protocol integrations substantially broadens this exposure. A comprehensive threat taxonomy categorizes these attacks by origin (direct or indirect), target (retrieval context, planning buffers, persistent state, or tool execution), and operational consequence (policy evasion, data exfiltration, unauthorized system action, or workflow redirection).

## Input validation and filtering

Input validation aims to neutralize or intercept hostile inputs before they enter the model's working context. Baseline controls apply size constraints, schema validation, string canonicalization, and known-pattern blocking. Higher-level defenses employ supervised classifiers to gauge prompt maliciousness. For example, Shaheer et al. (2025) train LSTM, feed-forward neural network, random forest, and Naive Bayes models on an augmented corpus derived from the HackAPrompt Playground, demonstrating viable application-layer detection independent of the underlying LLM.

Unified detection frameworks extend this scope. Lin et al. (2025) categorize prompt injections, backdoors, and adversarial examples under the umbrella of "Prompt Trigger Attacks" and introduce UniGuardian as an integrated defense. Their evaluations show efficient, accurate detection, including a single-forward architecture designed to unify screening and text generation. Ingress filtering of this kind can stop malicious prompts before sensitive developer directives or external context records enter the working prompt.

However, perimeter filtering cannot serve as a standalone solution. Classifiers inevitably face a precision-recall trade-off: strict thresholds risk blocking benign edge-case queries, while lenient settings let sophisticated attacks pass. Furthermore, front-end user message filtering fails to inspect secondary data introduced later via retrieval stores, user attachments, or external API endpoints. Because automated universal injections reliably bypass static classifiers (Liu et al., 2024), filtering must be applied across every boundary where external data enters the pipeline.

Validation is most effective as a containment and routing layer. It can identify high-risk payloads, route questionable inputs through restricted execution paths, strip unnecessary formatting, or trigger manual review. Passing input validation does not guarantee that a prompt is benign, but it lowers overall exposure and bounds the blast radius when downstream controls must engage.

## Instruction hierarchy and output controls

Instruction hierarchy addresses the structural challenge of authority inside prompt contexts. LLM architectures must reliably distinguish trusted system directives from untrusted user content, retrieved knowledge, and tool payloads. Tanveer (2026) advocates for an architectural division that clearly delineates trusted control channels from untrusted data channels. External information should enter the prompt explicitly framed as inert data for processing rather than authoritative instructions. The system prompt must firmly establish that third-party text cannot redefine core objectives.

This approach is conceptually superior to pure filtering because it directly targets the ambiguity between instructions and data, enabling systems to ingest arbitrary documents safely. Nevertheless, Tanveer (2026) notes that prompt-level hierarchy remains imperfect because both streams are ultimately tokenized through the same transformer attention mechanism. Prompt framing functions as an effective heuristic without providing formal or cryptographic isolation.

Output controls provide a complementary barrier by regulating downstream execution. Tanveer (2026) highlights the role of deterministic validation and policy mediation positioned between agent reasoning and actual tool calls. Applications can enforce strict structured schemas (such as JSON specifications) tied to explicit permissions, avoiding direct execution of raw model output. A dedicated execution layer can inspect every payload, rejecting calls that omit mandatory parameters or exceed defined operational scopes.

For tool-enabled agents, output controls significantly narrow the bridge between model compromise and real-world damage. They enforce least-privilege policies by restricting accessible tools and valid parameter ranges. At the same time, output validation cannot catch every semantic failure; a syntactically correct API call may still be malicious if broader contextual constraints are absent. Robust implementations combine both techniques: instruction hierarchy minimizes unauthorized influence on model reasoning, while output controls deterministically gate physical actions.

## Runtime defenses

Runtime defenses operate on the premise that sophisticated adversarial inputs will occasionally bypass perimeter filters and prompt framing. These mechanisms inspect retrieval events, agent reasoning trajectories, tool invocations, and response streams in real time to isolate anomalous activity. Tanveer (2026) emphasizes continuous adversarial monitoring across every execution layer—from initial ingestion and planning to tool dispatch—because an attack introduced at one stage may manifest harm only much later in the workflow.

Effective monitoring focuses on structural execution telemetry instead of token-level semantic parsing. Key telemetry points include data provenance across retrieved context items, classification scores at each stage, attempted deviations from initial task scope, and concrete tool invocation arguments. When runtime monitors detect anomalous behavior, the execution environment can terminate the session, restrict tool capabilities, quarantine external payloads, or escalate the action for human verification. This continuous tracking is vital for stateful agents, where persistent memory could otherwise store and propagate malicious state across multiple sessions.

Runtime monitoring also creates a closed feedback loop for iterative defense. Mathew (2024) highlights evaluation benchmarks such as PromptBench, AdvBench, AttackEval, INJECAGENT, and RobustnessSuite for measuring system resilience against diverse attack vectors. Similarly, Liu et al. (2024) demonstrate that continuous testing against gradient-based automated attacks prevents teams from relying on superficial robustness metrics. Tracking runtime anomalies provides the empirical data needed to calibrate detection thresholds and refine operational policies.

Implementing runtime defenses involves clear operational trade-offs. Deep telemetry collection can inadvertently capture sensitive data, while requiring human approval introduces latency. Furthermore, monitoring systems remain vulnerable to false positives and distributed attacks split across fragmented context windows. Consequently, runtime observation must be paired with preventive boundary controls and strict capability boundaries.

## Conclusion

Prompt injection and jailbreak vulnerabilities stem from a fundamental tension in modern LLMs: the flexibility of natural-language understanding conflicts with the need for rigid security boundaries. As Tanveer (2026) and Liu et al. (2024) demonstrate, agentic tool integrations expand the available attack surface, while automated attack synthesis can circumvent superficial defenses. No single mechanism provides a complete remedy for this structural challenge.

A resilient system relies on overlapping defensive tiers. Input validation filters high-probability threats at ingestion, while instruction hierarchies establish clearer boundaries between system instructions and external data. Downstream, deterministic output mediation prevents compromised reasoning from triggering unauthorized actions. Runtime monitoring envelops these preventive layers with continuous anomaly detection and telemetry logging, supplying the empirical feedback needed to counter emerging attack patterns. A layered architecture substantially elevates the cost of exploitation, contains downstream damage, and ensures the operational visibility required to maintain robust production systems.
